# SEO та індексація: план відновлення

Складено 27.09.2026 на основі наданого звіту Google Search Console, поточного коду та перевірки відкритих сторінок. Звіт GSC у вкладенні оновлений 21.09.2026, тому його числа є знімком на ту дату, а не поточним станом.

## Що підтверджено

- У наданому звіті GSC: 10 URL в індексі, 16 поза індексом; серед останніх 15 «Виявлено, не проіндексовано» і один `/blog` «Проскановано, але поки не проіндексовано».
- Звіт не містить прикладів 15 URL і не встановлює технічну причину для `/blog`. До URL Inspection не робити висновків про canonical, `noindex`, якість сторінки або доступність Googlebot.
- Поточний sitemap у коді містить 27 URL. Порівняти цю кількість із актуальним звітом GSC: різниця з 26 URL у знімку може бути наслідком змін після 21.09 або проблеми з читанням sitemap.
- Актуальний код містить спеціальне правило `SITE_LIVE`: без значення `true` `robots.txt` забороняє сканування всього сайту, а глобальні метадані додають `noindex`. У `.env.example` значення навмисно `false`. Не змінювати захист без підтвердження launch-готовності; перед будь-яким production-деплоєм перевірити саме deployed-відповідь.
- Анімація статистики на головній віддавала в початковому HTML нулі, хоча після запуску JavaScript показувала фактичні значення. Це підтверджено як у вихідному компоненті, так і в тексті, який отримує crawler. Замінено на серверно-рендерені значення.
- Sitemap задавав старі/спільні `lastModified`, а також `priority` і `changeFrequency`. Google використовує `lastmod`, коли дата точна й перевірювана, але ігнорує `priority` та `changefreq`. Непідтверджені дати й непрацюючі поля вилучено.
- Статті не мають окремого достовірного `dateModified`, тому з JSON-LD прибрано дату зміни, прирівняну до дати публікації. Також прибрано непідтверджену особу-засновника та надто вузький `areaServed` з глобальної/сервісної розмітки.
- У попередній локальній зміні додано узгоджену JSON-LD розмітку. Вона ще потребує production-перевірки після публікації.
- У попередньому скриншоті GSC для запиту «ai продавець» було 9 показів, 0 кліків і середня позиція 71,3 за вибраний тримісячний період. Це лише малий ранній сигнал, не достатній для прогнозу попиту.

## Пошуковий попит і конкурентне поле: попередня гіпотеза

У поточній ручній перевірці пошуку трапляються окремі українські пропозиції для AI-продажів і продажів у месенджерах: [Marichka AI](https://marichka.com.ua/), [Genis](https://geneiros.com/), [myAI](https://myai.com.ua/), [AI-Agent](https://ai-agent.com.ua/) та [Helveris](https://helveris.com/uk/). Це приклади активного конкурентного поля, а не виміряний рейтинг доменів чи оцінка їхнього органічного трафіку.

Пошукові кластери для перевірки в Search Console та окремому keyword tool:

| Кластер | Намір | Наявне покриття | Наступний крок |
|---|---|---|---|
| AI-продавець / AI-агент для продажів | Комерційний | Головна та `/ai-agent-dlya-prodazhiv` | Працювати з цими основними URL; не створювати дубльовані лендінги |
| AI для Instagram / Telegram / чат у месенджері | Комерційний, канал | Сторінки інтеграцій і матеріал про месенджери | Покращувати лише канали зі підтвердженим статусом; чітко розрізняти доступне й «за узгодженням» |
| AI-кваліфікація лідів / передача менеджеру | Інформаційний і комерційний | `/lead-qualification` та стаття блогу | Розвивати практичні матеріали: критерії кваліфікації, чеклист передачі контексту, шаблон сценарію |
| AI-автоматизація продажів для e-commerce, послуг і B2B | Комерційний, вертикальний | Є сторінки рішень і загальний гід | Поглиблювати унікальну галузеву конкретику; не обіцяти оформлення замовлення чи інтеграцію, якщо це не підтверджено продуктом |

Для цих кластерів немає перевірених у звіті обсягів пошуку, складності чи повного списку запитів. Наступний план контенту треба фіналізувати після експорту запитів і сторінок із Search Console та перевірки фактичних можливостей продукту. Не трактувати перелік конкурентів як доведений склад топ-10.

## Виконано локально

1. Статистика довіри тепер видима в HTML одразу, без залежності від анімації JavaScript.
2. Sitemap містить лише canonical URL сторінок; видалені непідтверджені дати, `priority` і `changeFrequency`.
3. Раніше додана JSON-LD схема збережена: `WebSite`/`Organization`, схема сторінок, блог-колекція, статті та профіль автора.

Production не змінювався. Після деплою необхідно перевірити sitemap, `robots.txt`, meta robots і canonical на живому домені.

## Пріоритетний план

### P0 — до наступного production-деплою

- Перевірити змінну `SITE_LIVE=true` саме в production-середовищі Vercel/хостингу.
- Після деплою відкрити `https://www.ministrysale.org/robots.txt`; переконатися, що сайт не закритий від Googlebot.
- На головній і пріоритетних URL перевірити відсутність `noindex`, HTTP 200 та canonical на `https://www.ministrysale.org/...`.
- Відкрити `https://www.ministrysale.org/sitemap.xml`; переконатися, що він читається, містить 27 актуальних canonical URL і не включає сторінки зі статусом `noindex`.

### P1 — розбір звіту GSC без припущень

- Оновити звіт «Індексування сторінок»; отримати фактичні URL 15 сторінок зі статусом «Виявлено, не проіндексовано».
- Для кожного URL класифікувати: потрібна до індексу canonical-сторінка; дублікат/alternate; URL із параметрами; `noindex`; редирект/404/5xx; сторінка без достатньої самостійної цінності.
- Для `/blog` виконати URL Inspection і live test: сканування дозволене, відповідь 200, user-declared canonical і Google-selected canonical, дата останнього обходу, наявність у відрендереному HTML та корисний основний вміст.
- Перевірити sitemap report: статус читання, час останньої обробки, кількість знайдених URL та приклади помилок.
- Лише після перевірки виправляти конкретні маршрути; не подавати однакові запити повторно, поки URL не змінений.

### P2 — індексація і контент

- Для перевірених сторінок, що мають бути в пошуку, підтвердити унікальність Title/H1/description, canonical, внутрішні посилання з тематично відповідних сторінок і наявність у sitemap.
- Пріоритет тем за наявними доказами: «AI-продавець», «AI-агент для продажів», кваліфікація лідів, AI у месенджерах. Розширювати блог після отримання звіту «Ефективність» із запитами, показами, CTR, позиціями та періодом; не створювати сторінки-дублікати лише заради кількості URL.
- Для сторінок інтеграцій і рішень оцінити, чи кожна має достатній унікальний зміст та окрему пошукову цінність; рішення про індексацію приймати після перегляду конкретних прикладів GSC.
- Перевірити звіти Manual actions, Security issues та Core Web Vitals. У наданому знімку ці дані або відсутні, або без достатньої деталізації.

## Порядок дій у Search Console після публікації

1. Властивість: використовувати `https://www.ministrysale.org/`; за потреби окремо звірити доменну властивість, яка охоплює www/без www і HTTP/HTTPS.
2. `Індексування → Файли Sitemap`: перевірити існуючий `/sitemap.xml`. Якщо статус успішний і дані актуальні, вдруге подавати його не потрібно; якщо sitemap не прочитаний або показує старий склад URL, надіслати `sitemap.xml` один раз.
3. `Перевірка URL → https://www.ministrysale.org/blog`: спершу «Перевірити опубліковану URL». Якщо 200, індексація дозволена, canonical правильний і зміст сторінки доступний - натиснути «Запросити індексування». Якщо перевірка показує проблему, спершу виправити її.
4. Так само перевірити головну `https://www.ministrysale.org/` після оновлення серверного HTML. Запитувати індексацію лише якщо live test підтверджує придатність.
5. Для 15 URL зі статусом «Виявлено, не проіндексовано» поки нічого масово не подавати. Спершу отримати приклади та для кожного визначити, чи він canonical і справді потрібен у Google. Якщо потрібний URL виправлено, виконати live test і надіслати запит лише для нього.
6. Не подавати `/start`, `/dyakuyemo`, `/oplata-uspishna` та legal-сторінки, позначені `noindex`; вони не призначені для індексації.
7. Після запитів перевіряти статус пізніше: запит лише ставить URL у чергу повторного обходу, не гарантує включення до індексу.

## Дані, потрібні для остаточного усунення 16 статусів

- 15 URL із таблиці прикладів GSC.
- URL Inspection для `/blog` та 3-5 найважливіших комерційних сторінок.
- Свіжий sitemap report і дата останньої обробки.
- Експорт Performance із періодом, кліками, показами, CTR, середньою позицією, запитами та сторінками.
- Підтвердження `SITE_LIVE` і перевірка production `robots.txt`/meta robots.
